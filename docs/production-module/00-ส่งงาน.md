## 1. บริบทก่อนเริ่ม

บริษัทมี **ระบบออกบิล (bill-system)** ที่พัฒนาไปแล้วและกำลังจะขึ้น Production
งานใหม่นี้คือ **โมดูล Production & Delivery** — ระบบติดตามออเดอร์ตั้งแต่รับ P.O. จนของขึ้นรถครบ

**ข้อกำหนดเรื่องขอบเขต — สำคัญมาก:**

- โมดูลนี้อยู่ใน **Portal Application เดียวกัน** กับระบบบิล บนฐานข้อมูลเดียวกัน
- **แต่ business logic แยกกันโดยสิ้นเชิง** — ห้ามแก้โค้ดฝั่ง Billing ที่เพิ่งทำเสร็จ
- **Product Master ใช้ตารางเดิมร่วมกัน ไม่ทำสำเนา ไม่ซิงก์** (แค่เพิ่ม field ที่ขาด)
- โมดูลนี้เป็นเจ้าของเฉพาะข้อมูลที่เกิดจากการผลิตและส่งของเท่านั้น

## 4. เริ่มที่ไหน

**ทำเฉพาะ P1 เท่านั้น ห้ามทำ P2 ขึ้นไปล่วงหน้า**

### P1 — โครงกระดูก (คีย์มือล้วน ยังไม่มี AI)

สร้าง:
- ตระกูลสินค้า (Product Family) + ตารางชื่อเรียกสินค้า (Alias) + หน้าจัดการ
- ออเดอร์ + รายการ + **ประวัติการแก้ (Revision)**
- ใบสั่งผลิต: สูตรผ้า · โครงสร้างสูงสุด 6 ชั้น · `spec_hash` · พิมพ์ 8 ชุด
- ประวัติกลาง (`events`)
- หน้าตั้งค่า: ไซส์ที่ผลิตได้ · แผนกและจำนวนชุด · สิทธิ์ผู้ใช้ · รูปแบบเลขที่เอกสาร

**จบ P1 เมื่อ:** ออกใบสั่งผลิตจากออเดอร์จริงได้ ใช้แทนกระดาษเดิมได้

### สิ่งที่ยังไม่มีข้อมูล — ให้ทำโครงสร้างรองรับไว้ ไม่ต้องรอ

- **ข้อมูลผ้าและโครงสร้างของทุกสินค้า** — เจ้าของจะส่งให้ทีหลัง
  ให้ออกแบบ `fabric_top/side/bottom` เป็น JSON มีโครงสร้าง และ `production_item_layers` ไว้ก่อน
- **รายการไซส์ที่ผลิตได้จริง** — ตั้งเป็นค่าตั้งค่า (config) ห้าม hardcode
  ร่างไว้ที่ 3 · 3.5 · 4 · 5 · 6 · สั่งตัด
- **ชื่อแผนกและจำนวนชุด** — ตั้งค่าเริ่มต้นเป็น ผ้า 3 · โครงสร้าง 3 · Box 2 (รวม 8)

## 5. กฎเหล็ก 8 ข้อ — ห้ามพลาด

1. **ยอดไม่ต้องเท่ากัน** — ผลิต ≠ ขึ้นรถ ≠ ค้าง ได้โดยชอบธรรม
   **ห้ามเขียน validation ว่า "ยอดไม่ตรง"** และห้ามแก้ใบผลิตย้อนหลังให้ตรงกับที่ขึ้นจริง
2. **ห้ามตัดยอดให้เอง** — ห้าม assume FIFO · คนเลือกเองว่าของที่ขึ้นรถตัดกับของค้างเก่าหรือออเดอร์ใหม่
   และต้อง**บันทึกไว้ว่าเลือกอะไร** (ตาราง `loading_allocations`)
3. **ห้ามเขียนทับประวัติ** — ลูกค้าแก้ออเดอร์กี่ครั้งเก็บทุกครั้ง หน้าจอโชว์ยอดปัจจุบัน แต่ประวัติต้องครบ
4. **ของค้างแยกใบใหม่เสมอ** — ขึ้นได้บางส่วน → ปิดใบเดิม สร้างใบใหม่ด้วยจำนวนที่เหลือ
   **ห้ามแก้ตัวเลขในใบเดิม** ไม่งั้นอายุของค้างรีเซ็ต ของที่ค้างมา 20 วันจะดูเหมือนเพิ่งค้างเมื่อวาน
5. **หลักฐานมาก่อนตัวเลข** — กระทบยอดไม่ได้ถ้ายังไม่แนบรูปใบขึ้นของที่ขีดแล้ว
6. **แก้หลังพิมพ์ = บันทึกลงระบบเสมอ แต่ไม่บังคับพิมพ์ใหม่** — *(Owner แก้กฎ 2026-08-29 ระหว่าง UAT S4 — ข้อความเดิมของเอกสารนี้ที่เขียนว่า "ต้องพิมพ์ใหม่ครบทั้ง 8 ชุด" ยกเลิกแล้ว)* หน้างานจริง: Owner โทรบอกพนักงานแล้วแก้กระดาษชุดเดิมด้วยปากกา — ระบบเก็บ digital history ครบ (CustomerPO Revision + Production Revision) และเตือนบนใบสั่งผลิตเมื่อ P.O. ต้นทางถูกแก้หลังออกใบ · การพิมพ์ Revision ใหม่เป็นทางเลือก ไม่ใช่เงื่อนไขบังคับ
7. **ตัดของค้างต้องอนุมัติ** — หัวหน้า/ผู้ดูแลระบบเท่านั้น · ห้าม Hard Delete เปลี่ยนสถานะเท่านั้น
8. **ตอบว่า "ไม่รู้" ได้** (สำหรับ P5) — ความล้มเหลวมีอย่างเดียวคือ *ไม่รู้แต่แกล้งทำเป็นรู้*

## 6. สามเรื่องที่ต้องเข้าใจก่อนออกแบบ Schema

**1 · `spec_hash` คือกุญแจของการพิมพ์ใบสั่งผลิต**
คำนวณจาก รุ่น + กุ๊น + ความหนา + ผ้าทั้งสามตำแหน่ง + ทุกชั้นโครงสร้าง
รายการที่ hash ตรงกัน = บล็อกเดียวกันตอนพิมพ์ (ต่างกันแค่ไซส์)
**ถ้าเก็บสูตรผ้าเป็นข้อความก้อนเดียว จะจัดบล็อกไม่ได้เลย**

**2 · ผ้าต้องจัดบรรทัดอัตโนมัติ สูงสุด 2 บรรทัด**
เทียบสเปกทั้งสามตำแหน่งแล้ววางเป็นตาราง 2 คอลัมน์:
- เหมือนกันหมด → 1 บรรทัด `ผ้า บน/ข้าง/ล่าง`
- สองอันเหมือน หนึ่งต่าง → 1 บรรทัด 2 คอลัมน์ `ผ้า บน-ล่าง | ผ้า ข้าง`
- ต่างกันทั้งสาม → 2 บรรทัด (บน|ข้าง แล้ว ล่าง)

ขา · ล้อ · อุปกรณ์อื่น **ไปอยู่ในหมายเหตุ ไม่ใช่ช่องผ้า**

**3 · `events` เก็บ `customer_id` ทุกแถว**
แม้จะหาย้อนได้จาก entity เพราะหน้าประวัติของบริษัทจะถูกเปิดบ่อยที่สุด
ถ้าต้อง join ห้าตารางทุกครั้ง หน้านั้นจะช้าจนไม่มีใครใช้

## 7. ขั้นตอนก่อนลงมือเขียนโค้ด

ใช้กติกาเดียวกับที่ตกลงไว้ตอนทำระบบบิล — **ห้ามเริ่มเขียนโค้ดทันที** ให้ทำตามลำดับนี้ก่อน:

1. อ่านเอกสาร 1–3 ให้ครบ
2. สรุปความเข้าใจกลับมาให้เจ้าของตรวจ
3. ระบุจุดที่ยังไม่ชัดหรือขัดกัน
4. เสนอ Database Schema ของโมดูลนี้
5. เสนอโครงสร้าง API / Backend
6. เสนอ Screen Flow ของ P1
7. เสนอแผนการพัฒนา P1 แบ่งเป็น sprint / task
8. ระบุคำถามที่ต้องการคำตอบก่อนเริ่ม

**รอ Approval จากเจ้าของก่อนเขียนโค้ดจริง**
และ**ห้ามเพิ่ม Scope เอง** — ถ้าคิดว่าควรมี feature เพิ่ม ให้เสนอพร้อมเหตุผลและผลกระทบ แล้วรออนุมัติ

## 8. คำถามที่ต้องถามเจ้าของก่อน / ระหว่างทำ

1. ระบบบิลใช้ stack อะไร framework อะไร — โมดูลนี้ต้องใช้ตัวเดียวกัน
2. โครงสร้างตาราง `products` ปัจจุบันมี field อะไรบ้าง — ต้องเพิ่ม `family_id`, `form`, `material`, `color`, `thickness`, `status`
3. ระบบสิทธิ์ผู้ใช้เดิมเป็นยังไง — โมดูลนี้ใช้ต่อได้ไหม
4. ใช้ printer แบบไหน — ใบสั่งผลิต A4 ตั้ง / ใบขึ้นของ **A4 นอน** (ไม่ใช่กระดาษต่อเนื่องเหมือนใบกำกับภาษี)
5. เก็บรูปที่แนบไว้ที่ไหน — ต้องเก็บถาวร ห้ามลบ
