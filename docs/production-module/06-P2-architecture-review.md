## 1. Entities — สิ่งที่เปลี่ยนจาก 04

### 1.1 เพิ่ม `LoadingDrop` (จุดส่ง) — แก้จุดที่ 04 เคยตัดออก

04 เคยเสนอว่าไม่ต้องมี entity จุดส่ง (group by ลูกค้าบน line ตรงๆ พอ) — **ถอนข้อเสนอนั้น** เหตุผลจากการทบทวน:

- เที่ยวรถจริงมี "ลำดับจุดส่ง" (ไปไหนก่อน-หลัง) ซึ่ง group-by ให้ไม่ได้ — ต้องมี `seq` ต่อจุดส่ง
- ใบขึ้นของ A4 แนวนอนพิมพ์เรียงตามจุดส่ง + ยอดรวมต่อจุด — มี Drop เป็นแถวจริงทำให้โครงสร้างใบพิมพ์ตรงกับข้อมูล ไม่ต้อง derive
- รูปหลักฐาน/หมายเหตุบางอย่างเป็นของ "จุดส่ง" ไม่ใช่ของทั้งเที่ยวหรือของรายการเดียว

โครงสุดท้ายที่เสนอ: **`LoadingTrip` → `LoadingDrop` (ลูกค้า/สาขา/ลำดับ) → `LoadingLine` → `OutstandingAllocation`** — LoadingLine ย้าย `customerId/branchId` ไปอยู่ที่ Drop

### 1.2 `LoadingLine` — เพิ่ม `qtyPlanned` แยกจาก `qtyLoaded`

04 มีแค่ `qtyLoaded` — ไม่พอ เพราะความจริงธุรกิจคือเลข 4 ตัวที่ต่างกันได้หมด (ผลิต ≠ แผนขึ้น ≠ ขึ้นจริง ≠ ค้าง):

| เลข | อยู่ที่ไหน | ใครกำหนด |
|---|---|---|
| ลูกค้าต้องได้ (ยอดจริงปัจจุบัน) | `CustomerPOLine.qtyCurrent` | source of truth เดิมของ P1 — รวมกรณีแก้ออเดอร์หลังพิมพ์โดยไม่ออก Rev ใหม่แล้ว |
| ฝ่ายผลิตถูกสั่ง | `ProductionItem.qty` (Rev ปัจจุบัน) | snapshot ตอน Confirm/Rev |
| แผนจะขึ้นเที่ยวนี้ | `LoadingLine.qtyPlanned` | คนจัดเที่ยว (ตอน DRAFT) |
| ขึ้นจริง | `LoadingLine.qtyLoaded` | คนหน้างานยืนยันยอดรวมเอง (V1 ไม่ OCR) |
| ค้าง | derive: `Outstanding.qtyOriginal − Σ allocation` | ระบบคำนวณ ไม่มีใครพิมพ์แก้ตรงๆ |

หน้า reconcile ต้องโชว์ warning เมื่อ `qtyCurrent ≠ ProductionItem.qty` (เกิดได้โดยชอบธรรมจากกฎ "แก้หลังพิมพ์ไม่บังคับ Rev ใหม่" ของ S6) — คนตัดสินใจเองว่ายึดตัวไหน ระบบห้ามเดา

### 1.3 ที่คงเดิมจาก 04 (ยืนยันแล้วว่าถูก)

`sourceType FRESH/OUTSTANDING/ADHOC` · snapshot ชื่อสินค้า/SKU บน line (pattern `productionLabelSnapshot` เดิม) · `photoPaths` ตาม pattern `poImagePaths` · `version` CAS บน LoadingTrip (pattern `CustomerPO.version`) · ADHOC = free text V1 ไม่บังคับ resolve ย้อนหลัง (เพิ่มได้ทีหลังแบบ additive ถ้าต้องการ ไม่ใช่การตัดสินใจที่ต้องรีบ)

## 2. Outstanding — challenge 3 ทางเลือกตามที่ Owner สั่ง

โจทย์บังคับ: ระบบต้องตอบย้อนหลังได้ครบ 4 คำถาม — *ค้างจากออเดอร์ไหน · ตั้งแต่เมื่อไร · เคยขึ้นไปเท่าไร/ครั้งไหนตัดจากอะไร · เหลือเท่าไร*

| | **A: ใบเดียวคงที่ + สมุดจดการตัด** (append-only allocations) | **B: ปิดใบเก่า-ออกใบใหม่** (parent→child ทุกครั้งที่ขึ้นบางส่วน) | **C: ไม่มีตาราง — คำนวณสดล้วน** |
|---|---|---|---|
| ค้างจากออเดอร์ไหน | `customerPoLineId` ตรงๆ | ตาม chain ถึง root | join ได้ |
| ตั้งแต่เมื่อไร (อายุ) | `openedAt` แถวเดียว **ไม่เคยถูกแก้** | ต้องเดินขึ้น chain หา root (พลาดแล้วอายุรีเซ็ต = ผิดกฎข้อ 4 แบบเงียบๆ) | **ไม่มีคำตอบ** — ไม่มี event "เริ่มค้าง" เก็บไว้ |
| เคยขึ้น/ครั้งไหนตัดจากอะไร | อ่าน allocations ตรงๆ (แต่ละแถว: เที่ยวไหน วันไหน กี่ชิ้น ใครเลือก) | ต้องประกอบจากหลายใบ + allocations อยู่ดี | ต้องมีตาราง allocation อยู่ดี → ไม่ได้ลดอะไร |
| เหลือเท่าไร | `qtyOriginal − Σ` (derive, ไม่มีใครแก้เลขได้) | เลขบนใบ leaf (แต่ต้อง filter ใบที่ถูก supersede — query ทุกจุดพลาดได้) | คำนวณสด |
| ตัดของค้างแบบอนุมัติ (กฎข้อ 7) | มีแถวให้ CANCEL + เหตุผล ตรงๆ | ได้ แต่ต้องตัดที่ leaf ถูกใบ | **ทำไม่ได้** — ไม่มีแถวให้ตัด |

**ข้อสรุป: C ตกรอบ** (ตอบเรื่องอายุกับการตัดของค้างไม่ได้เลย) — เหลือ A กับ B ซึ่งเป็น**การตีความกฎข้อ 4 สองแบบ** จึงเป็น Owner decision (D1 ด้านล่าง) — ฝั่งเทคนิคยืนยัน **แนะนำ A**: เจตนาของกฎข้อ 4 คือ "เลขต้นทางห้ามแก้ + อายุห้ามรีเซ็ต" ซึ่ง A ทำได้แข็งแรงกว่า (2 ค่านั้น immutable ที่แถวเดียว ไม่มี chain ให้เดินพลาด) ส่วนคำว่า "แยกใบใหม่" ในกฎ สะท้อนอยู่แล้วที่**เที่ยวรถแต่ละเที่ยวเป็นเอกสารใหม่ของตัวเอง** — การตัดแต่ละครั้งคือแถว allocation ใหม่เสมอ ไม่มีการแก้ของเก่า

## 3. Reconcile transaction (ธุรกรรมเดียวจบ — spec)

```
เงื่อนไขก่อนเริ่ม (เช็คฝั่ง server ทั้งหมด ไม่ใช่แค่ UI):
- CAS สถานะเที่ยว: LOADED → RECONCILED (updateMany WHERE status=LOADED — กดซ้ำ/ชนกัน = no-op ตาม pattern confirmPrintRevision)
- ทุก LoadingLine ต้องมีรูป ≥ 1 (กฎข้อ 5 หลักฐานมาก่อนตัวเลข) และ qtyLoaded กรอกแล้ว
- ทุกชิ้นที่ขึ้นต้องถูกชี้ที่มา: Σ allocation ของ line = qtyLoaded (แบ่งได้ระหว่างตัดของใหม่/ตัดของค้างหลายใบ — คนเลือกเอง ไม่มี FIFO)

ใน transaction:
1. สร้าง OutstandingAllocation ตามที่คนเลือก (append-only)
2. Outstanding ใบไหน Σ ครบ qtyOriginal → status=CLOSED (derive แล้ว mark เพื่อ query เร็ว)
3. ยอดที่ควรได้ (qtyCurrent) ยังเหลือหลังรวมทุกเที่ยว → เปิด Outstanding ใหม่ (ถ้ายังไม่มีใบ OPEN ของ line นั้น)
4. AuditLog: RECONCILE 1 แถว/เที่ยว + correlationId เดียวกันทุก entity ที่โดนแตะ
```

แก้หลัง RECONCILED: **ห้ามแก้แถวเดิม** — ทำ "รายการปรับปรุง" ชดเชย (append-only, gate ที่แอดมิน, เหตุผลบังคับ) ตามหลัก immutable เดียวกับ Revision ทั้งระบบ — อันนี้เป็นคำตอบเทคนิคที่ปลอดภัยชัดเจน ไม่ต้องให้ Owner ตัดสิน

## 4. จุดเชื่อมกับระบบเดิม

- **Cancellation (doc 05)**: picker FRESH/OUTSTANDING กรองออเดอร์/ใบสั่งผลิตที่ `cancelledAt ≠ null` ออกเสมอ · ยกเลิกออเดอร์ที่มี Outstanding เปิดอยู่ → พาไปหน้าตัดของค้างแบบอนุมัติ ไม่ปิดเงียบ
- **ประวัติ (S5)**: เพิ่ม module `LoadingTrip`/`Outstanding` เข้า `classify()`/`EVENT_LABELS` เดิม — โครงหน้าประวัติรองรับอยู่แล้วไม่ต้องรื้อ
- **ใบขึ้นของ A4 แนวนอน**: เพิ่ม profile ใหม่ใน `PRINT_PROFILES` (additive) — **ห้ามแตะ** profile `continuous` 9×11 (ผ่านการทดสอบกระดาษจริง มีคำสั่งห้ามแตะเด็ดขาด) และ `a4` เดิมที่ Owner จูน margin ไว้แล้ว
- **P6/Billing ในอนาคต**: LoadingLine เก็บ `customerPoLineId` + snapshot ไว้แล้ว → วันหน้า match กับ invoice ได้โดย**ไม่ต้องมี FK ไปตาราง Billing ตอนนี้เลย** (coupling = ศูนย์ ตามกติกา)
- Running number เที่ยวรถ: `getNextSeq("TRIP", ...)` ของเดิม

# Owner Decision Sheet (ภาษาหน้างาน)

> เฉพาะเรื่องที่ต้อง Owner ตัดสินจริง — เรื่องเทคนิคที่มีคำตอบปลอดภัยชัดเจนตัดออกแล้ว

### D1 — บัตรของค้าง จะจดแบบไหน?

ลองนึกภาพ: ลูกค้าสั่ง 10 ใบ เที่ยวแรกขึ้นไป 4 เหลือค้าง 6 · เดือนถัดมาขึ้นอีก 2

- **แบบ ก. (แนะนำ)**: มี "บัตรค้าง 6 ใบ" ใบเดียว เลข 6 กับวันที่เริ่มค้าง**ห้ามใครแก้ตลอดชีวิต** แล้วมีสมุดแนบท้ายจดว่า "เที่ยววันที่ X เอาไป 2" — อยากรู้เหลือเท่าไหร่ระบบลบให้ดูเอง (เหลือ 4) อายุค้างนับจากวันแรกวันเดียวชัดๆ
- **แบบ ข.**: ทุกครั้งที่ขึ้นบางส่วน ปิดบัตรเก่า-ออกบัตรใหม่ด้วยเลขที่เหลือ (บัตร 6 → ปิด, ออกบัตร 4) — ตรงตัวอักษรกฎ "ของค้างแยกใบใหม่เสมอ" แต่บัตรงอกเรื่อยๆ และอายุค้างต้องไล่ย้อนไปหาบัตรต้นตระกูล ถ้าโค้ดจุดไหนไล่พลาด ของค้าง 20 วันจะดูเหมือนเพิ่งค้าง (สิ่งที่กฎข้อ 4 กลัวที่สุด)

**แนะนำ ก.** — ปกป้องเจตนาของกฎ (เลขห้ามแก้ อายุห้ามรีเซ็ต) ได้แข็งแรงกว่าตัวอักษรของกฎ

### D2 — ของถือว่า "เริ่มค้าง" ตั้งแต่เมื่อไหร่? (จุดเริ่มนับอายุ)

- **ก. วันที่ลูกค้าต้องการของ** — ครอบคลุมสุด แต่ออเดอร์ที่ยังไม่ได้เริ่มผลิตเลยก็จะขึ้นเป็น "ค้างส่ง" ด้วย (ปนกันระหว่าง "ผลิตไม่ทัน" กับ "ส่งไม่ครบ")
- **ข. วันยืนยันเริ่มผลิต** — กลางๆ แต่ระบบไม่มีเหตุการณ์ "ผลิตเสร็จ" จึงยังไม่รู้จริงว่าของพร้อมส่งเมื่อไหร่
- **ค. (แนะนำ) วันแรกที่กระทบยอดแล้วพบว่าขึ้นไม่ครบ** — ตรงความหมาย "ค้าง**ส่ง**" ที่สุด (มีการส่งเกิดขึ้นแล้วและไม่ครบ) และเป็นครั้งแรกที่มีมนุษย์+หลักฐานรูปยืนยันตัวเลขจริง — ข้อแลก: ออเดอร์ที่ไม่เคยขึ้นรถเลยจะไม่อยู่ในลิสต์ "ของค้าง" (จะอยู่ในมุมมอง "ยังไม่เคยจัดส่ง" แยกต่างหากแทน)

### D3 — ควรมีปุ่ม "ยกเลิกใบสั่งผลิตแยกใบ" ไหม? (ไม่ยกเลิกทั้งออเดอร์)

เคสจริง: ออกใบสั่งผลิตผิด (เลือกรายการผิด/สเปคผิดทั้งใบ) แล้วอยากยกเลิกเฉพาะใบนั้นเพื่อออกใหม่ โดยออเดอร์ลูกค้ายังอยู่ — ตอนนี้ทำไม่ได้เลย ใบผิดจะค้างในระบบตลอด
**แนะนำ: มี** — โครงสร้างจาก doc 05 รองรับอยู่แล้ว (ฟิลด์เดียวกัน) เพิ่มแค่ปุ่ม+เหตุผล แทบไม่มีต้นทุนเพิ่ม

### D4 — ยกเลิกออเดอร์แล้ว "เปิดกลับ" ได้ไหม?

**แนะนำ: ไม่ได้ใน V1** — ลูกค้าเปลี่ยนใจ = สร้างออเดอร์ใหม่ (กดครั้งเดียวถึงหน้าเพิ่มออเดอร์อยู่แล้ว) ประวัติสะอาด ไม่มีเคสก้ำกึ่งว่าใบสั่งผลิตที่โดน cascade ไปแล้วต้องฟื้นตามไหม — ถ้าหน้างานเจอปัญหาจริงค่อยเพิ่มแบบ additive ทีหลังได้

### D5 — หลังเริ่มผลิตไปแล้ว ใครกดยกเลิกออเดอร์ได้?

สิทธิ์ปัจจุบันในระบบ (ตั้งไว้ตั้งแต่ S1): พนักงานกดยกเลิกได้เหมือนแอดมิน
- **ก. (แนะนำ) คงเดิม — พนักงานกดได้ทุกจังหวะ** แต่บังคับเหตุผล + คำเตือนแรงตามจังหวะ (ตรงกับหน้างานจริงที่รับโทรศัพท์ลูกค้าโดยตรง และตรงกับที่ Owner เขียนใน requirement ว่า "ลูกค้ายังยกเลิกได้" โดยไม่ได้จำกัดคน)
- **ข.** หลังเริ่มผลิตแล้ว ให้เฉพาะแอดมิน (พนักงานต้องโทรหา Owner ก่อน)
